# Извлечение лабораторных показателей v0.1

TL;DR: облачный провайдер выбирается через `AI_PROVIDER`. Для Яндекса используйте
`lab-extract configure PROFILE_UUID --cloud --daily-budget 20` и отдельное разрешение
профиля из [инструкции Yandex](yandex-ai.md). Старый флаг `--openai` ниже работает
только при выбранном OpenAI. Обработка создаёт кандидатов, а не подтверждённые анализы.

Worker обрабатывает уже импортированные PDF, PNG и JPEG, не меняя оригиналы
в vault. Все новые показатели требуют явного review через Telegram, CLI или
Sheets. Извлечение не подтверждает медицинские факты автоматически и не ставит
диагнозы. Вес в v0.1 поступает из WHOOP.

## Включение и ручной backfill

Сначала примените миграции к выбранной базе обычным `uv run alembic upgrade head`.
Единственная новая миграция — `0008_lab_extraction`, после `0007_google_sheets`.
Команды ниже — инструкция оператору, реализация/тесты их на живой базе не запускали.

```bash
uv run health-agent lab-extract configure PROFILE_UUID
uv run health-agent lab-extract run PROFILE_UUID
uv run health-agent lab-extract status PROFILE_UUID
```

`configure` включает локальный worker для конкретного существующего профиля.
По умолчанию OpenAI выключен. Повторный `configure` без `--openai` также выключает
cloud; счётчики запросов не сбрасываются. `--disabled` отключает worker без удаления
очереди и результатов. `run` одновременно обнаруживает новые страницы и делает
ограниченный backfill старых. Повторяйте его, пока backlog не разобран; один запуск
не обещает обработать весь архив.

Для разрешения передачи текста лабораторной страницы в OpenAI:

```bash
uv run health-agent lab-extract configure PROFILE_UUID --openai --daily-budget 20
uv run health-agent lab-extract run PROFILE_UUID --limit 4 --cloud-limit 2
```

Используются существующие Settings OpenAI: ключ/приватный key file, model,
reasoning effort и output-token limit. Ключ читается только перед первым cloud
вызовом; `status`, локальный parser и discovery его не читают. Настройка не запускает
API сама по себе. Не включайте cloud для чужого профиля без разрешения владельца.

## Автоматическая обработка новых документов

После `configure` существующая [автоматизация](runbooks/automation.md) обнаруживает
job `lab_extraction` для включённого профиля. Порядок: Drive/Gmail/WHOOP → extraction
→ Sheets. Каждый job независим: сбой коннектора не запрещает обработку уже
импортированных документов. Telegram работает отдельно; новые завершённые импорты
попадут в extraction на следующем scheduled run (обычно раз в четыре часа).
Connector/import транзакции не вызывают OCR/OpenAI и не ждут cloud.

Discovery добавляет не более500 ранее необработанных страниц за запуск. Worker
обрабатывает4 страницы по умолчанию, максимум20. Cloud: максимум2 запроса за запуск
по умолчанию, жёсткий максимум10;20 в день по UTC по умолчанию, максимум100;
не более3 зарезервированных попыток на страницу за все версии extractor. Резервация
считается использованной даже при отказе/ошибке: реальные расходы могут отличаться.
Уменьшение дневного бюджета не обнуляет уже использованное. Откат часов не выдаёт
новый дневной бюджет. `--cloud-limit 0` временно запрещает cloud в данном запуске.

## Что сохраняется и что остаётся неизвестным

Для каждого кандидата сохраняются исходное имя, числовой токен/единица,
неизменённый excerpt страницы, номер страницы, связь с документом и source records,
исходный reference text и отдельный печатный флаг `H/L/↑/↓/*`, если он есть.
Однозначный печатный диапазон low–high также хранится численно. Confidence —
не калиброванная вероятность достоверности, а явная эвристика маршрута:
local0.8, cloud0.6, неизвестный analyte0.4. Review reason хранит local/cloud и v1;
page job — extractor version, digest текста, последний method/model и счётчики.

`reference_low/high` всегда относятся к исходной `source_unit`, не автоматически
к `normalized_unit`. Если review конвертировал единицу значения, downstream должен
сначала привести reference bounds в совместимые единицы или показать исходный
диапазон отдельно. `source_flag` остаётся печатным флагом исходника даже в correction
lineage, а не заключением о новом исправленном значении.

Известные analyte/unit пары нормализуются только при явном подтверждении.
Неизвестные названия остаются `unmapped_…`, неизвестные единицы не конвертируются;
для подтверждения нужна явная корректировка в поддерживаемый analyte/unit.
Значения с `<`, `>`, `≤`, `≥` не выдаются за точное число. Исходные знаки, decimal
commas и диапазоны не угадываются. Parser не добавляет возрастные/половые референсы,
не восстанавливает отсутствующую дату и не снимает конфликт медицинских дат.

Эти данные дают downstream insight layer подтверждённые значения, единицы,
референсы и provenance для объяснения нормы/отклонения/нехватки данных. Общая
картина, значимость динамики и безопасные дальнейшие действия — отдельный insight
layer, не результат extractor. Отсутствие кандидатов не доказывает отсутствие
анализов; review исходника и оценка OCR/layout качества всё ещё нужны.

## Ошибки, restart и retry

Неизвестный analyte можно явно сопоставить через локальный CLI, просмотрев исходник:

```bash
uv run health-agent review list --profile-id PROFILE_UUID
uv run health-agent review correct OBSERVATION_UUID --profile-id PROFILE_UUID --value 5.1 --unit mmol/L --canonical-name glucose
```

Указывайте только подтверждённый вами supported canonical analyte/unit; неправильная
пара или чужой профиль отклоняются без изменения фактов. Создаётся отдельная verified
correction со связью на неизменённый исходник. Telegram `/correct` в v0.1 меняет
только значение/единицу: для mapping используйте этот CLI или Sheets. Никакого
сопоставления по свободному тексту и молчаливой medical verification нет.

`status` выводит config/counts/budget; `status PROFILE_UUID --details` добавляет
до20 незавершённых страниц текущей версии: document UUID, page, extractor version,
state и фиксированный safe_error. Без текста, имени файла или model output.
`--limit 1..100 --offset N` позволяет листать backlog. UUID из этой команды
используется для retry; `cloud_outcome_unknown` требует отдельного acknowledgment.
`run` выводит `status=succeeded`,
если обнаруженная очередь разобрана, или `deferred`, если остались queued,
waiting_cloud/needs_attention. Это не означает, что кандидаты уже подтверждены.
Cloud opt-in/лимит оставляют страницы waiting_cloud. Плохой исходник, непригодный
текст, превышение bounds, refusal/incomplete/invalid output требуют внимания.

Отклонённые cloud-запросы показываются только фиксированными кодами без ответа
провайдера, request ID или текста исключения:

- `cloud_quota_exhausted` — закончился доступный баланс/квота; пополните баланс или
  квоту, затем явно повторите страницу;
- `cloud_rate_limited` — провайдер временно ограничил частоту; дождитесь снятия
  ограничения и повторите позже;
- `cloud_auth_required` — проверьте API key и разрешения проекта, затем повторите;
- `cloud_request_rejected` — запрос не принят как некорректный; перед retry проверьте
  поддерживаемую model/configuration и совместимость SDK/API.

После quota/auth/rate-limit ошибки worker не делает новых cloud-запросов в этом
запуске, но продолжает локальную обработку оставшихся страниц. Каждая уже
зарезервированная попытка по-прежнему расходует дневной и lifetime budget. Ошибки
timeout/transport/5xx остаются `cloud_outcome_unknown`: для них сохраняется запрет
на неявный retry и требуется `--acknowledge-unknown`.

```bash
uv run health-agent lab-extract retry PROFILE_UUID DOCUMENT_UUID
uv run health-agent lab-extract retry PROFILE_UUID DOCUMENT_UUID --acknowledge-unknown
```

Перед запросом durable job получает `cloud_in_flight` и расходует бюджет. При
неизвестном ответе/обрыве процесса следующий worker выставляет
`cloud_outcome_unknown`; автоматического повторного запроса нет. Оператор явно
подтверждает риск повторного расхода через `--acknowledge-unknown`. Retry не
обнуляет3-попыточный лимит и не переоткрывает completed результаты. Прерванный
локальный этап может безопасно повториться. PostgreSQL profile lock и claim token
не позволяют двум worker одновременно публиковать результаты одного профиля.
Pending/verified/rejected/исправленные исходные строки участвуют в дедупликации:
backfill не меняет решения и не «воскрешает» отклонённое.

Миграция вниз от0008 отказывается удалять существующую extraction config/очередь
или source flags: это защищает provenance и fences расходов. Для rollback с
данными нужен отдельный операторский план, а не удаление таблиц наугад.

## Privacy и технические пределы

Непустой сохранённый текст страницы переиспользуется. Пустая страница может быть
прочитана из hash-verified vault и обработана Apple Vision на Mac. Текст, на который
уже ссылаются наблюдения, не заменяется. OCR использует фиксированный subprocess
без shell, timeout30s; оригинал≤50MiB, raster≤25M pixels, страницы1–100,
текст≤60000 символов. Нужны доступные локальные `/usr/bin/swift`/Vision и языки
ru-RU/en-US. Другие ОС без injected OCR получают безопасный `ocr_unavailable`.

Cloud получает только текст одной страницы≤12000 символов, не файл; до40
кандидатов, excerpt≤500 символов. Strict Responses JSON schema, `store=false`,
30s timeout, без SDK retries/tools, hashed profile identifier. `store=false`
не означает гарантированное отсутствие хранения на стороне провайдера.
Текст страницы может содержать персональные данные; включение cloud разрешает
передачу всей ограниченной страницы, а не только числовых результатов.

CLI/automation логи содержат только UUID/счётчики/фиксированные safe codes.
Оригиналы, page text и evidence намеренно остаются в приватной локальной базе/vault.
Временные OCR файлы создаются приватно и удаляются при нормальном завершении/
ошибке; аварийное убийство процесса может оставить приватный temp-каталог.
Автоматической TTL-очистки этого каталога нет. Тесты используют synthetic fixtures,
fake OCR/OpenAI и disposable PostgreSQL: качество настоящих OCR/model/layout и
фактическая задержка/стоимость требуют отдельной разрешённой проверки оператором.
