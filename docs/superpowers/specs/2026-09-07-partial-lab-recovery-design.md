# Восстановление пропущенных строк анализов

TL;DR: корректная строка не теряется из-за ошибочной соседней. Восстановить уже
оплаченные ответы локально, затем проверить сложные PDF существующим геометрическим
разборщиком. Не создавать новую систему и не обнулять очередь ради зелёного статуса.

Пользователь утвердил этот подход командами «Продолжай», после явного описания
сохранения корректных строк, восстановления сложных таблиц и сверки дат/исходников.
Повторное согласование технического документа не требуется: пользователь прямо
просит выполнять, не вовлекать без необходимости и не останавливаться на планах.

Выбран отдельный результат частичного извлечения: принятые кандидаты и число
отклонённых строк. Проверка каждого кандидата остаётся прежней строгой проверкой;
ошибка внешнего JSON/envelope по-прежнему отклоняет весь ответ. Старый строгий API
сохраняется. Новая обработка сервиса использует частичный результат и оставляет
needs_attention/cloud_partial_output, если хотя бы одна строка отклонена.
Альтернативы — повторить всё облаком или ослабить проверку фрагментов — не решают
потерю хороших строк либо снижают проверяемость; они не выбраны.

Добавить операторский import-cached для локального сохранённого ответа Яндекса:
явные профиль, документ, страница; точное совпадение page_text с сохранённой
страницей, правильный завершённый envelope. Только уже известная ошибка
cloud_invalid_output или повторное частичное восстановление; неизвестный исход,
running/completed и оборванный ответ не переоткрываются. Импорт без сетевых запросов,
без фиктивных cloud reservations и без изменения расходов/числа попыток. Любое
частичное восстановление остаётся неполным, даже если все имеющиеся кандидаты
валидны: оно не доказывает полноту оригинала. Review обязателен, даты не угадываются.

Публикация использует существующие блокировки, ограничения на 40 кандидатов
страницы за все версии и дедупликацию, включая rejected/verified/corrections.
Исходные документы, текст, даты и прошлые решения review неизменны. Метод и причина
новых кандидатов явно отличаются от живого облачного запроса. Без миграции,
смены identity очереди, новых сервисов или интеграций.

Приёмка: изолированные тесты смешанного ответа, неверного envelope, профиля,
страницы, изменённого текста, повторного импорта, rejected-строк, лимитов и rollback;
проверка обеих облачных интеграций без живого API. После ревью — резервная копия,
реальное локальное восстановление и частный отчёт о новых кандидатах/датах/остатке.
Нельзя называть кандидатов подтверждённой историей или заявлять полное распознавание
без сверки с оригиналами. Локальные чужие правки не коммитить.

Конкретизация сложного PDF после проверки оригинала: поддержать физически
размеченную таблицу с точным заголовком «Параметр / Значение / Ед. измер. /
Реф.значение / Представление», когда перед заголовком есть объединённые строки.
Сохранить геометрию как новую v2 evidence, не менять старую v1. Общий и мономерный
пролактин — разные показатели; буквальные мЕд/л сохраняются отдельной единицей
mU/L, без объединения с международными или массовыми единицами. Подпись врача
не заменяет отсутствующую дату забора. Это реализация уже согласованного восстановления
сложных таблиц, не новый продуктовый сценарий.
