# Health Agent Lean v0.1 Implementation Plan

> **Status:** Superseded by the approved full-product v1 scope; do not execute.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Быстро получить работающую локальную систему, которая читает медицинский Drive-архив, показывает проверенные анализы и регулярно собирает данные WHOOP, Oura и COROS.

**Architecture:** Один Python-проект на Mac, PostgreSQL и Metabase в Docker. Drive является read-only источником; нормализованные данные хранятся в PostgreSQL, сырые ответы — локальными файлами, а сомнения проверяются через отдельную Google-таблицу.

**Tech Stack:** Python 3.12, PostgreSQL 16, Docker Compose, Google Drive/Sheets APIs, PyMuPDF с OCR fallback, официальные WHOOP/Oura API, официальный COROS MCP, Metabase 0.63.16.

## Global Constraints

- Никаких записей во входящую Drive-папку.
- Никаких приватных API устройств и паролей от аккаунтов.
- Токены — в локальных gitignored-файлах `0600`; Keychain не требуется.
- Никакой медицинской интерпретации в 0.1: только сбор, проверка и визуализация фактов.
- Не строить универсальную платформу, публичный API, event bus, vector database или собственный UI.
- Реальный результат после каждого этапа важнее полноты инфраструктуры.

## Этап 1: Вертикальный срез на нескольких PDF

- [ ] Создать Git-проект `health-agent`, минимальный `pyproject.toml` и `compose.yaml` с PostgreSQL и Metabase.
- [ ] Создать только необходимые таблицы: `documents`, `lab_tests`, `lab_results`, `review_items`, `sync_runs`.
- [ ] Подключить корневую Drive-папку по OAuth в режиме read-only и получить рекурсивный inventory без привязки к именам подпапок.
- [ ] Скачать локально три PDF, классифицированные как лабораторные, не изменяя Drive.
- [ ] Извлечь текст локально; OCR запускать только для PDF без пригодного текстового слоя.
- [ ] Распознать лабораторные строки, сохранив значение, единицу, референс, дату, файл и страницу.
- [ ] Всё неоднозначное направить в `review_items`; уверенные результаты выборочно сравнить с оригиналом вручную.
- [ ] Показать первый рабочий график одного реально найденного показателя в Metabase.

**Gate:** этап завершён, когда хотя бы три документа дают корректную историю показателей со ссылками на источники, повторный импорт не создаёт дублей, а Drive не получил ни одного write-вызова.

## Этап 2: Полный медицинский архив и Google Sheets

- [ ] Прогнать тот же pipeline по текущим 122 PDF; неизвестные типы индексировать, но не пытаться структурировать сверх лабораторных результатов.
- [ ] Исправить только повторяющиеся классы ошибок, обнаруженные на реальных документах; не писать универсальный медицинский parser заранее.
- [ ] Создать отдельную Google-таблицу вне входящего архива с листами `Ключевые показатели`, `История анализов`, `Требует проверки`, `Источники`.
- [ ] Реализовать простой цикл: пользователь подтверждает/исправляет строку → следующий запуск импортирует решение → таблица и графики обновляются.
- [ ] Выбрать показатели для дашборда из реально найденных данных и построить многолетние графики с референсами конкретной лаборатории.

**Gate:** все 122 текущих PDF имеют один из понятных статусов — `processed`, `needs_review`, `duplicate` или `failed`; ни один сомнительный результат не попадает в график.

## Этап 3: Wearable-коннекторы — параллельные ветки

После создания общего минимального контракта `fetch → save raw file → normalize → advance cursor` три задачи выполняются параллельно и не меняют файлы друг друга.

- [ ] **WHOOP:** OAuth, полный доступный backfill, затем incremental sync через официальный Developer API. Сначала попробовать зафиксированный whoopyy-клиент; отказаться от него только при реальной проблеме лицензии, установки или официальности endpoint.
- [ ] **Oura:** OAuth, доступный backfill и incremental sync через официальный API v2; refresh token заменять атомарно.
- [ ] **COROS:** однодневный feasibility spike официального MCP. Если он поддерживает исторические окна и повторный фоновый доступ — использовать MCP; иначе импортировать официальные FIT-файлы и явно показать пробел по daily health/sleep.
- [ ] Для каждого источника сохранить сырой ответ локально, нормализовать дневные показатели/сон/тренировки и доказать повторным запуском отсутствие дублей.

**Gate:** каждый источник независимо показывает дату последнего успешного обновления. Ошибка одного не мешает двум другим.

## Этап 4: Два дашборда

- [ ] **Обзор:** свежесть источников, сон, HRV, resting HR, recovery/readiness, тренировки и последние ключевые анализы.
- [ ] **Анализы крови:** выбранные показатели по годам, исходная единица, динамика, индивидуальный референс каждой точки и ссылка на PDF.
- [ ] Ограничить Metabase адресом `127.0.0.1`; не разрабатывать отдельную локальную страницу.

**Gate:** пользователь открывает два понятных дашборда на Mac и может от каждой лабораторной точки перейти к источнику.

## Этап 5: Минимальная регулярность

- [ ] Добавить один простой launchd job: медицинский импорт, WHOOP/Oura/COROS sync и обновление Sheets несколько раз в день.
- [ ] Добавить одну команду ручного запуска и короткий статус: когда обновлялся каждый источник и что сломалось.
- [ ] Добавить ежедневный локальный `pg_dump` с хранением последних семи копий; проверить восстановление в отдельную тестовую базу.
- [ ] Написать одностраничный runbook: старт, остановка, ручная синхронизация, повторная авторизация и восстановление.

**Gate:** после входа в macOS система обновляется сама; ручной запуск и восстановление не требуют правки кода.

## Что сознательно откладывается

- Telegram и Health-агент;
- Google Calendar и подготовка визитов;
- медицинские советы и причинные корреляции;
- сложное извлечение текста консультаций и исследований;
- публичный API и MCP поверх базы;
- облачный хостинг, несколько пользователей и круглосуточная доступность;
- автоматизированное управление секретами и сложная система backup encryption.

## Порядок параллельной работы

```text
Этап 1 → Этап 2 ─┬─ WHOOP ─┐
                 ├─ Oura ──┼─→ Этап 4 → Этап 5
                 └─ COROS ─┘
```

Этапы 1 и 2 выполняются последовательно, потому что они задают реальный формат данных. После них три wearable-коннектора делаются параллельно. Внутри Этапа 4 общий SQL-контракт создаётся первым, после чего два дашборда можно строить параллельно.
